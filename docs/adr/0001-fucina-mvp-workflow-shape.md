# Forma del workflow MVP di Fucina

Fucina è uno strato sottile sopra Sandcastle: possiede label GitHub, convenzioni di workflow, prompt, caricamento configurazione e setup CLI, mentre Sandcastle possiede esecuzione agenti, sandboxing, branch strategy, session handling e integrazione provider. L’MVP supporta solo GitHub.com e usa GitHub Actions, non una GitHub App; una GitHub App resta una possibile evoluzione futura se Actions diventa limitante.

Fucina si installa nei repository target con un workflow che usa `npx @vekexasia/fucina@<version>` pinnato, non come dipendenza del repository. `fucina install` scrive i workflow e `.fucina/config.json`, crea o aggiorna le label, non committa mai, non richiede working tree pulito e non sovrascrive file esistenti senza conferma o `--force`; `install-labels` resta un comando secondario di manutenzione. `upgrade` aggiorna workflow e label, aggiunge solo chiavi di config mancanti, non sovrascrive mai valori esistenti e lascia invariato `agentCliVersion`.

L’MVP usa solo workflow triggerati da label operative `fucina:*`. Non esiste una label di readiness: se una label non cambia il comportamento di Fucina, non appartiene all’MVP. Le trigger label sono button label one-shot: Fucina rimuove solo la label che ha triggerato la run quando quella run parte. `fucina:blocked` rappresenta l’ultima run fallita o rifiutata e viene rimossa automaticamente al retry; `fucina:in-progress` è una singola label di stato visibile, non un lock di coda. Tutti i workflow Fucina condividono concurrency repository-wide di GitHub Actions con `cancel-in-progress: false`, quindi le run Fucina sono sequenziali e GitHub Actions fa da coda. Non esiste `fucina:queued`.

Il set iniziale di label è `fucina:explore`, `fucina:implement`, `fucina:review`, `fucina:address-feedback`, `fucina:in-progress` e `fucina:blocked`. `fucina:update-branch` è volutamente fuori dall’MVP perché non è core per “issue dentro, PR fuori” e la risoluzione dei conflitti è più rischiosa. `fucina:implement` vale solo per issue aperte e crea una draft PR dalla default branch del repository usando branch `fucina/issue-<number>-<slug>` e body PR `Closes #<number>`. Rifiuta issue chiuse, sub-issue, parent issue con sub-issue, PR già esistenti che chiudono la issue, branch Fucina già esistenti e run senza commit. Il titolo PR è `Implement #<number>: <issue title>`, e Fucina commenta sulla issue con il link alla PR creata.

`fucina:review` vale per PR aperte, è read-only, può girare su draft PR, pubblica una vera GitHub PR Review con event `COMMENT`, e non edita file, non committa, non pusha, non approva, non richiede modifiche e non risolve thread. Il suo diff canonico è il GitHub PR diff API; i commenti inline vengono filtrati alle righe presenti in quel diff, e la review resta riuscita se i commenti inline invalidi vengono scartati ma il summary è valido. `fucina:address-feedback` vale solo per branch PR interne aperte, considera unresolved review threads e commenti top-level della PR, può committare fix, può rispondere quando utile, può declinare feedback motivando, non marca mai thread come resolved, e riesce se produce almeno un commit o commento utile. Usa diff/commenti PR come contesto, fa checkout della branch interna per modificare, e pusha con `--force-with-lease` contro lo starting head SHA; se la branch avanza, blocca e chiede retry.

Fucina ha una sola definizione di Authorized Actor: se `FUCINA_ALLOWED_ACTORS` è configurato, solo quegli username GitHub sono autorizzati; altrimenti sono autorizzati i collaborator del repository con permesso `write`, `maintain` o `admin`. Solo Authorized Actor possono triggerare Fucina. Le run non autorizzate rimuovono la trigger label, commentano e aggiungono `fucina:blocked`. `AGENT_PAT` è opzionale; Fucina usa `AGENT_PAT || GITHUB_TOKEN` e fallisce con messaggio chiaro se i permessi richiedono un PAT.

L’MVP installa tre piccoli workflow invece di un singolo workflow con permessi larghi: un workflow issue per `explore` e `implement`, un workflow PR review per `review`, e un workflow PR mutation per `address-feedback`. Tutti condividono la stessa concurrency repository-wide. I workflow PR usano `pull_request_target`; review ha `contents: read` e `pull-requests: write` ma non `contents: write`, mentre mutation ha permessi write e rifiuta PR da fork prima di checkout o esecuzione. Le PR da fork possono far girare solo review in modalità read-only/API-safe: niente checkout o esecuzione del codice del fork, il contenuto della PR è trattato come non trusted, e solo le instruction Fucina trusted dal base repo possono influenzare il prompt.

Fucina supporta i provider Sandcastle `claudeCode`, `codex` e `pi`. La precedenza di configurazione è: variabili d’ambiente, poi `.fucina/config.json` opzionale, poi errore per valori richiesti mancanti. Lo schema minimo è flat: `agent`, `model`, `agentCliVersion` e opzionale `maxIterations`; `agent`, `model` e `agentCliVersion` sono valori espliciti obbligatori salvo siano forniti da env. `maxIterations` defaulta a `1` ed è configurabile da config/env. Fucina installa automaticamente il CLI del provider scelto alla versione pinnata `agentCliVersion`; non si affida al workflow target per preparare i CLI provider. Agent Profile multi-file avanzati sono una direzione futura, non MVP.

Fucina possiede la forma finale del prompt. Core task, safety policy e output contract non sono sovrascrivibili. I repository possono aggiungere istruzioni append-only tramite `.fucina/instructions/safety.md`, `.fucina/instructions/global.md` e `.fucina/instructions/<mode>.md`; queste sono instruction, non sostituzioni complete del prompt. Fucina non include automaticamente `AGENTS.md`, `CLAUDE.md`, `CONTEXT.md` o ADR nei prompt; i file nativi degli agenti restano nativi del provider, e le instruction cross-agent stanno sotto `.fucina/instructions/`. Prompt command expansion non è una feature Fucina; gli agenti possono eseguire comandi tramite il proprio tooling dove consentito. L’output agente usa un singolo tag XML contenente JSON; nell’MVP non c’è extraction retry pass, quindi output malformato blocca la run.

Fucina protegge i file che possono influenzare le istruzioni da prompt injection. `sensitiveInstructionPaths` defaulta a `.fucina/**`, `.github/workflows/**`, `AGENTS.md`, `CLAUDE.md`, `.claude/**`, `.codex/**` e `.pi/**`; `.fucina/config.json` può sovrascrivere completamente questa lista, ma non esiste override via env. Se una PR modifica sensitive paths e l’autore della PR non è un Authorized Actor, la review si blocca con `fucina:blocked` e commenta un comando full-SHA copiabile: `/fucina trust-instructions <head-sha>`. Lo slash command è l’unico slash command dell’MVP, gira nella stessa concurrency repository-wide, deve essere postato da un Authorized Actor, vale solo per quello specifico full head SHA, triggera direttamente la review, rimuove eventuale label `fucina:review` rimasta e rimuove `fucina:blocked` in caso di successo. Se i sensitive paths vengono modificati di nuovo in un nuovo commit, serve una nuova approvazione slash.

Tutti i commenti e messaggi user-visible di Fucina sono in inglese e usano il nome Fucina. Fucina non posta commenti di start. I commenti di failure sono brevi e uniformi: label fallita, reason breve, link alla workflow run e istruzione di retry; non includono output dettagliato dell’agente o secrets. I commenti di successo dipendono dal mode: `explore` posta l’analisi sulla issue, `implement` commenta con il link alla draft PR, `review` posta una GitHub PR Review, e `address-feedback` posta reply utili e/o un summary top-level quando appropriato. Fucina non include mai environment variables o secrets nei prompt, passa all’agente tutti i commenti issue/PR visibili al workflow come contesto, non gestisce milestone, assignee, project o chiusura issue, e si affida a `Closes #<number>` perché GitHub chiuda le issue al merge della PR.
